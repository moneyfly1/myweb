# 用户使用状态与「在线」判定说明

> 对应功能：后台 → 用户管理 → 列表里的**使用状态**列（在线 / 活跃 / 近期用过 / 静默），以及
> `GET /api/v1/admin/activity/summary`、`GET /api/v1/admin/users?activity=online|active|idle|silent`。

## 一、为什么要单独设计

自研客户端可以发**真心跳**（前台/后台、进程存活、精确设备 ID），那是高置信度信号。

但用户换成第三方客户端（v2rayN / Clash / Shadowrocket / sing-box / Hiddify…）之后：

- 这些客户端**不会**、协议上也无法给你的面板发心跳；
- 你能观察到的只有两件事：**它来拉订阅了**、**它在节点上有连接/流量**。

所以「用户是否在用」只能是**被动推断**，产品上必须如实展示判定依据，否则会被当成「在线统计不准」。

## 二、三种信号（可靠度递增）

| 信号 | 说明 | 粒度 | 采集位置 |
|---|---|---|---|
| ① 订阅拉取 | 客户端按 `Profile-Update-Interval` 回拉订阅，说明客户端还活着、配置在更新 | 分钟~小时（面板下发默认 60 分钟） | 订阅入口 `MarkSubscriptionFetch` |
| ② 节点侧流量增量 | 有流量增长 = 真在用，最诚实的「使用」证据 | 心跳周期（30–60 秒） | `POST /api/v1/agent/heartbeat` 的 `traffic_up/down` |
| ③ 节点侧按用户连接数 | 此刻真的连着节点 → 秒级「在线」 | 秒级 | 同上，`users[]` 数组 |

**注意：①≠在用**。有人写脚本定时刷订阅但从不连节点；**只有 ②③ 能证明在真用**。

## 三、三档状态

| 状态 | 判定 | 依据 |
|---|---|---|
| 🟢 在线 `online` | 90 秒内节点侧上报该用户活跃连接数 > 0 | ②（需节点能区分用户） |
| 🔵 活跃 `active` | 60 分钟内有过订阅拉取 **或** 节点上报 | ①或② |
| 🟡 近期用过 `idle` | 24 小时内有信号，但最近 60 分钟没有 | ①或② |
| ⚪ 静默 `silent` | 24 小时内无任何信号（含从未使用） | — |

窗口可调（代码内变量，`internal/services/activity`）：`OnlineTTL=90s`、`ActiveWindow=60m`、`IdleWindow=24h`。

> 为什么活跃窗口是 60 分钟而不是几分钟：第三方客户端按 `Profile-Update-Interval`（面板默认下发 60 分钟）
> 才回拉一次订阅，窗口比更新周期短会**系统性低估在用人数**。要真正的秒级"在线"，靠的是节点侧按用户上报（②）。

## 四、数据存在哪

- **实时状态**：Redis（zset 存时间戳，天然支持「最近 N 分钟有信号」的集合运算）
  - `cboard:act:active`：任何信号（成员=用户 ID，分数=Unix 时间）
  - `cboard:act:online`：节点上报连接数>0
  - `cboard:act:conns:<uid>`（TTL 90s）、`cboard:act:meta:<uid>`（UA/IP/归属地/格式/次数，TTL 7 天）
  - Redis 不可用时**自动降级为进程内存储**（功能可用，但多实例不共享、重启即失效）
- **快照兜底**：数据库表 `user_usage_states`（每用户一行，节流写入，默认 60 秒最多一次）
  - 用于 Redis 重启/换机后仍能看到「最后拉订阅时间/客户端/IP」等信息

## 五、接口

| 接口 | 用途 |
|---|---|
| `GET /admin/users?activity=online\|active\|idle\|silent` | 按使用状态筛选（SQL 用 ID 集合过滤，分页总数准确） |
| `GET /admin/users?...`（列表项 `activity` 字段） | `state / online_conns / last_sub_at / last_sub_ua / last_sub_ip / last_sub_location / last_sub_format / last_sub_software / sub_fetch_count / last_node_report_at` |
| `GET /admin/activity/summary` | `{online, active, idle}` 计数 + 窗口（秒/分/时）与判定依据说明 |
| `GET /admin/users/:id/activity` | 单个用户状态（排障用） |
| `POST /api/v1/agent/heartbeat` | 节点心跳；新增可选 `users[]`（见下） |

## 六、节点侧：当前限制与升级路径（重要）

**现状：自建节点是单凭据设计。** 安装脚本生成的是 `"users": [ { "uuid": "${UUID}" } ]`，
一套 UUID/密码被所有订阅用户共用 → 节点侧**无法区分是谁在连**，`users[]` 只能为空，
「在线」状态因此暂时不会出现（列表里显示为活跃/静默，属正常）。

**要让「在线」变成真数据**，需要把自建节点升级为多用户（面板侧已就绪，届时无需再改面板）：

1. **按用户发凭据**：生成订阅配置时为每个用户生成独立 UUID/密码（写入节点配置的 `users[]`，
   并带上 `name = "u_<userID>"` 之类的稳定标识）；
2. **下发用户列表**：节点定期从面板拉取「该节点上应有的用户」，重写 sing-box / Xray 配置并重启；
3. **节点侧采集**：在 `cboard-agent-heartbeat.sh` 里增加采集
   - sing-box：`clash_api` 的 `/connections`，按 `metadata.user` 聚合连接数与上下行
   - Xray：开启 stats/api 后用 `xray api statsquery --pattern "user>>>"`（需要先在配置里启用
     `"stats": {}`、`"api": {"tag": "api"}` 与 `policy`）
   结果随心跳上报：
   ```json
   {"install_id":"...","token":"...","traffic_up":1024,"traffic_down":2048,
    "users":[{"user_id":12,"conns":3,"up":10240,"down":40960}]}
   ```
   （`user_id` / `email` / `username` 三种标识任选其一，面板会批量解析）
4. 面板会据此写入 Redis 在线集合与 `user_usage_states.online_conns`。

## 七、常见坑

1. **别把「活跃」当「在线」**：第三方客户端做不到秒级心跳，「在线」只能来自节点侧（③）。
2. **订阅拉取≠在用**：脚本刷订阅会造成误判；流量增长（②）才是最诚实的证据。
3. **多节点聚合**：一个用户可能同时在多个节点上，任一节点上报 `conns>0` 即为在线。
4. **性能**：`MarkSubscriptionFetch` 只写 Redis（微秒级）+ 节流落库，绝不阻塞订阅响应；
   列表页一次批量取状态（不是逐用户往返）。
5. **隐私**：UA/IP/归属地属于个人信息，采集与展示需与隐私政策一致。
6. **Redis 清理**：菜单 4（深度清理缓存）按本项目键前缀删除，不会误删其它服务的键；
   键前缀统一为 `cboard:act:`。

## 八、设备维度（用户端「设备管理」）

设备页与用户级同源，但**设备没有独立心跳**：每次该设备回拉订阅时，`device_manager` 才会把
`LastSeen` / `LastAccess` 更新为当前时间。所以设备活跃度 = **这台设备最近一次回拉订阅的时间**。

### 8.1 为什么不能用固定窗口（实测数据）

生产库 6562 台设备的统计：**单台设备的平均回拉间隔普遍是 4~15 小时**，远大于面板下发的
`Profile-Update-Interval`（60 分钟）——多数客户端只在打开 App / 手动刷新时才回拉，不按 interval 轮询。

某真实用户（有 49 台设备、天天在用）设备的平均间隔：235 / 283 / 450 / 597 / 689 / 742 / 860 / 903 分钟。

- 用固定 **1 小时**：该用户「活跃设备 = 0 台」❌（用户实测反馈）
- 用固定 **24 小时**：又退化成原来那个分不清「在用 / 不用」的粗口径 ❌

### 8.2 现在的口径：按设备自身节奏自适应

```
阈值 = clamp(2 × 该设备平均回拉间隔, 1 小时, 24 小时)
平均回拉间隔 = (现在 - 首次出现) / 累计回拉次数
```

| 状态 | 判定 | 含义 |
|---|---|---|
| 🟢 活跃 `active` | 距上次回拉 ≤ 阈值 | 还在按自己的节奏回拉 → 仍在使用 |
| 🟡 近期用过 `recent` | ≤ 24 小时（超出自身节奏） | 近期用过，当前没动静 |
| ⚪ 离线 `offline` | > 24 小时（含从未） | 卸载 / 换客户端 / 已不用 |

- **乘 2**：允许偶发漏掉一个周期（关机、切网络、App 没打开）仍算在用
- **上下限护栏**：新设备样本少不会被算出极小阈值；一年只拉过一次的也不会被一直当成活跃
- 接口同时返回 `activity_basis`（人话依据）、`activity_avg_interval_sec`、`activity_threshold_sec`，
  前端悬停即可看到，例如：*"最近一次回拉在 2.4 小时前，平均约每 4.7 小时回拉一次，处在正常节奏内（阈值 9.4 小时）"*

### 8.3 实现要点（踩过的坑）

1. 判定只写一份：`internal/services/device.ActivityOf`；前端只做展示映射，不自己算
   （早期前端按 24 小时自算 `isOnline`，与后端口径不一致）。
2. **筛选/统计不走 SQL**：先用 `COALESCE(last_seen,last_access) >= ?` 做筛选与计数时，
   实测出现自相矛盾（逐台显示"活跃"，`state=active` 却查不到它）——根因是 SQL 的时间比较
   依赖数据库里时间字符串的格式（时区/精度/写入方不同就比错）。现在全量取出后在 Go 里判定，
   一致性由设计保证；设备数受设备数上限约束，性能无影响。
3. 前端把绝对时间换成**相对时间**（"3 分钟前 / 2 小时前 / 3 天前"，秒数由后端给），
   筛选下拉改为服务端参数 `state=`，避免"只过滤当前页"导致分页与总数打架。
4. 旧字段 `online` / `total_online` 保留（24 小时口径）不破坏老前端；
   页面展示用 `total_active` / `total_recent` / `total_offline`。

### 8.4 要设备级"秒级在线"怎么办（当前都没做）

1. **自研客户端加独立心跳接口**（带 `X-MF-Device-Id` 这类安装级唯一 ID），面板实时打点 —— 最准，
   且能顺带拿到前台/后台、版本、在线时长；第三方客户端仍走上面的三档推断；
2. 节点侧按用户上报连接数（需节点多用户化）—— 只能算到**用户维度**，一个用户多设备时无法区分设备。
